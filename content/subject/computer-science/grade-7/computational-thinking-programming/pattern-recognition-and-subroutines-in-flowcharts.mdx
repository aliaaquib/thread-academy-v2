Good problem-solvers do not treat every problem as brand new. They look for what they have seen before — and good programmers do the same with their flowcharts.

<Definition term="Pattern recognition">
  Spotting repetition or similarity in a problem so you can reuse one solution instead of inventing many.
</Definition>

## Key ideas

### See the repetition

Imagine a flowchart that prints a party invitation three times — once for each guest. The steps "print name, print date, print venue" appear again and again. That repetition is a pattern, and patterns are a hint: this chunk of steps deserves a name of its own.

### Sub-routines: name it, reuse it

A **sub-routine** is a named chunk of steps that does one job. The main flowchart *calls* it wherever it is needed, using a special symbol: a rectangle with double vertical lines (the predefined-process symbol). When the sub-routine finishes, flow returns to where it was called.

### Sub-routines can take inputs

A sub-routine can accept a value each time it is called — called a **parameter**. `greet(name)` prints "Hello, " followed by whatever name it is given: greet("Asha") prints "Hello, Asha", greet("Omar") prints "Hello, Omar". Same steps, different result.

### Why bother?

Three reasons programmers love sub-routines: the main flowchart stays short and readable; a fix in one place fixes every call; and a well-named sub-routine explains itself — `print_invite` tells you what happens without showing the steps.

<WorkedExample title="Trace the calls">
  Main flow: START → call print_invite → call print_invite → STOP. The sub-routine print_invite prints one invitation and returns.

  Trace: START, call print_invite (jump into it, print invitation, RETURN to main), call print_invite again (print invitation, RETURN), STOP.

  **Answer:** Two invitations are printed, even though the steps are written only once. Adding a third guest means adding one call, not rewriting the steps.
</WorkedExample>

<ImportantNote title="Common mistakes">
  - **Copying the steps instead of calling** Correction: pasting the same steps three times means fixing a mistake three times — call the sub-routine instead.
  - **A vague name** Correction: name the sub-routine after its job — print_invite, not thing1 — so the main flow reads like instructions.
  - **Forgetting it must end** Correction: a sub-routine finishes with RETURN (back to the caller), not STOP — STOP would end the whole program.
</ImportantNote>

## Practice

<PracticeQuestions>
  <PracticeItem question="Which flowchart symbol calls a sub-routine?">
    The predefined-process symbol: a rectangle with double vertical lines on the left and right sides.
  </PracticeItem>
  <PracticeItem question="A flowchart prints a 5-line border of stars, then a title, then the border again. Where is the pattern?">
    The border-printing steps repeat — that repeated chunk is the pattern, and it should become a sub-routine called twice.
  </PracticeItem>
  <PracticeItem question="What is a parameter, in one sentence?" hint="Think of greet(name) being called with different names.">
    A value passed into a sub-routine when it is called, so the same steps can work on different data.
  </PracticeItem>
  <PracticeItem question="After a sub-routine finishes, where does the flow go?">
    Back to the main flow, at the step right after the call — that is what RETURN means.
  </PracticeItem>
</PracticeQuestions>

<Summary>
  - Pattern recognition: spotting repetition or similarity so you can reuse one solution instead of inventing many.
  - Sub-routine: a named chunk of steps that does one job, called from the main flow with the double-lined rectangle symbol.
  - Parameters let one sub-routine work on different data at each call.
  - Watch out for: copying steps instead of calling, vague names, and ending a sub-routine with STOP instead of RETURN.
