Programs rarely work the first time. Professionals expect that — so they build software in a cycle: plan a little, code a little, test, fix, and repeat. Testing is not an afterthought; it is half the job.

<Definition term="Bug">
  An error in a program that makes it behave incorrectly or crash. Finding and fixing bugs is called debugging.
</Definition>

## Key ideas

### The development cycle

Real software is built in loops, not one straight line:

1. **Analyse** — what should the program do, and for whom?
2. **Design** — sketch the solution (flowcharts welcome here).
3. **Code** — write it in a programming language.
4. **Test** — run it with different inputs and check the results.
5. **Fix** — repair what testing found, then test again.

Each round improves the program. Even your classroom projects should go round at least once: first draft, test, fix.

### Prototypes: build small first

A **prototype** is an early, small version of a product that might have only some of the features. Teams build one to check whether the design is suitable, whether the inputs and outputs are appropriate, and whether it meets the requirements — before committing to the full build. A prototype that fails teaches you cheaply; a full product that fails teaches you expensively.

### Planning the project, not just the code

Before coding, teams agree on the practical side too:

- **Requirements** — what exactly must the finished product do?
- **Tasks** — who does what, so everyone knows their job and has a suitable task.
- **Deadlines** — what must be finished by when, so the project lands on time.
- **Inputs, processes, outputs** — identified up front and used consistently through the program.

Without this, people start tasks that cannot be completed because another task is unfinished — the classic project traffic jam.

### Test like a detective, not a fan

Beginners test with the input they *hope* works — the "happy path". Testers deliberately try to break things, using three kinds of data:

- **Normal data** — ordinary, expected input. Score of 65 for a pass/fail program.
- **Boundary data** — values at the edges, where bugs hide. Exactly 50 and exactly 49 for "pass if score ≥ 50".
- **Invalid (erroneous) data** — wrong-type or nonsense input. Typing "ten" instead of 10, or a negative score.

A **test table** keeps it organised — a formal record with four columns: a description of what is being tested, the input data, the expected output, and the actual result. Written down, it proves what was tested and stops the same tests being repeated.

### Debugging like a professional

When code misbehaves, do not stare at it hoping for inspiration. Work systematically:

1. **Read the code line by line** and check it makes sense.
2. **Use a checklist** — keywords, operators, variables: is each one correct? (Line 1: missing final bracket; Line 4: average := should be average =.)
3. **Trace the variables** — write down variable names and their values at each step, and check they are correct.

This methodical approach finds both syntax errors (code that breaks the language's rules and will not run) and logic errors (code that runs but does the wrong thing — like Total should be + number3, not - number3).

### Two kinds of bug

- **Syntax error** — the code breaks the language's rules, so it will not run at all. Python tells you immediately (e.g. a missing bracket). Annoying but easy to find.
- **Logic error** — the code runs fine but gives the wrong answer. The program does what you *said*, not what you *meant*. These are the sneaky ones — only testing catches them.

<WorkedExample title="Build a test table">
  Program: prints "Pass" if score ≥ 50, else "Fail".

  | Test | Data | Type | Expected | Actual | Pass? |
  |---|---|---|---|---|---|
  | 1 | 65 | normal | Pass | Pass | ✓ |
  | 2 | 50 | boundary | Pass | Pass | ✓ |
  | 3 | 49 | boundary | Fail | Fail | ✓ |
  | 4 | "ten" | invalid | error handled | crash | ✗ |

  **Answer:** Tests 1–3 pass, but test 4 exposes a bug — the program crashes on text input instead of handling it. That failing test is valuable: it tells the programmer exactly what to fix next.
</WorkedExample>

<ImportantNote title="Common mistakes">
  - **Only testing the happy path** Correction: normal data alone misses edge bugs — always add boundary and invalid tests.
  - **Fixing without re-testing** Correction: every fix can break something else. Re-run the full test table after each change.
  - **Treating a failed test as failure** Correction: a failed test is a success for the tester — it found a bug before a user did.
</ImportantNote>

## Practice

<PracticeQuestions>
  <PracticeItem question="A program gives a discount for ages 65+. Give one boundary test value and say why.">
    65 itself — it sits exactly on the edge of the rule, which is where off-by-one bugs hide. (64 is the other boundary.)
  </PracticeItem>
  <PracticeItem question="Is this a syntax error or a logic error: the program runs but prints the average as 250 instead of 25?">
    A logic error — the code runs, so the syntax is fine; the calculation itself is wrong.
  </PracticeItem>
  <PracticeItem question="Give one example of invalid data for a program that asks for your age.">
    "twelve" (text instead of a number), or -5 (a nonsense age) — input the program was not designed for.
  </PracticeItem>
  <PracticeItem question="Why do developers test, fix, and test again instead of doing it once?">
    Because fixes can introduce new bugs — re-testing confirms the fix worked and nothing else broke.
  </PracticeItem>
  <PracticeItem question="What is a prototype, and why build one?">
    An early, small version with only some features — it lets the team check the design and requirements cheaply before building the full product.
  </PracticeItem>
  <PracticeItem question="A test table has four columns. Name them.">
    Description of what is being tested, the input data, the expected output, and the actual result.
  </PracticeItem>
  <PracticeItem question="List the three steps of systematic debugging.">
    Read the code line by line; use a checklist (keywords, operators, variables); trace variable names and values to check they are correct.
  </PracticeItem>
</PracticeQuestions>

<Summary>
  - Software is built in a cycle: analyse, design, code, test, fix — then round again.
  - Test with normal, boundary and invalid data; record it all in a test table.
  - Syntax errors stop code running; logic errors run but answer wrongly — only testing catches them.
  - Watch out for: testing only the happy path, and fixing code without re-testing.
