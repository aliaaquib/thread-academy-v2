A flowchart is a picture of a plan. Before anyone writes code, they sketch what the program should do — using standard shapes, so that anyone who reads the sketch understands it the same way.

<Definition term="Flowchart">
  A diagram that shows the steps of an algorithm in order, using standard shapes joined by arrows.
</Definition>

## Key ideas

### Plan on paper first

Code is fiddly: one wrong character and nothing works. A flowchart lets you get the *logic* right before you fight with syntax. If the plan is wrong on paper, it will be wrong in code — so programmers draw first, then type.

### The shapes everyone agrees on

There are only a few shapes to learn, and they are the same all over the world:

- **Oval** — start and stop. Every flowchart opens with a START oval and closes with a STOP oval.
- **Rectangle** — a process. Something the computer does, like "add 1 to total".
- **Parallelogram** (a slanted rectangle) — input or output. "Read the score" or "print the result".
- **Diamond** — a decision. A question with a yes/no answer, like "is the score 50 or more?".
- **Arrows** — flow lines. They show which step comes next, so every arrow needs a clear direction.

### Reading a flowchart

Start at the START oval and follow the arrows, top to bottom. When you reach a diamond, answer its question and take the matching path — then keep going until you hit STOP.

**Key term — algorithm:** A set of step-by-step instructions for solving a problem. A flowchart is one way to *show* an algorithm; code is another way to *write* it.

<WorkedExample title="Trace the flowchart">
  A flowchart for a test result: START → INPUT "read the score" → DECISION "score ≥ 50?" → Yes → OUTPUT "print Pass" → STOP; No → OUTPUT "print Fail" → STOP.

  The score is 65. Follow the arrows: START, read 65, ask "is 65 ≥ 50?" — yes — so take the Yes path, print "Pass", STOP.

  **Answer:** The flowchart outputs "Pass". If the score had been 40, the No path would print "Fail".
</WorkedExample>

<ImportantNote title="Common mistakes">
  - **Arrows with no direction** Correction: every arrow must point somewhere — an arrow without a clear direction leaves the reader guessing which step comes next.
  - **Missing START or STOP** Correction: every flowchart opens with a START oval and closes with a STOP oval, so the reader knows where the algorithm begins and ends.
  - **Rectangle for input/output** Correction: "read the score" is input, so it belongs in a parallelogram — rectangles are for processes only.
</ImportantNote>

## Practice

<PracticeQuestions>
  <PracticeItem question="Which shape is used for a decision, such as 'is the number even'?">
    The diamond — decisions always go in diamonds, with one arrow in and two arrows out (Yes and No).
  </PracticeItem>
  <PracticeItem question="A flowchart step says 'print the total'. Which shape should it be?">
    A parallelogram — printing is output, and input/output steps use the slanted rectangle.
  </PracticeItem>
  <PracticeItem question="Trace this flowchart: START → 'set count to 0' → 'add 1 to count' → decision 'is count = 3?' → No loops back to 'add 1 to count'; Yes → STOP. What is count when it stops?" hint="Go round the loop, counting each pass.">
    3 — count becomes 1, then 2, then 3; at 3 the decision answers Yes and the flowchart stops.
  </PracticeItem>
  <PracticeItem question="Why do programmers draw a flowchart before writing code?">
    To get the logic right first — a mistake is easier to spot and fix in a drawing than in code.
  </PracticeItem>
</PracticeQuestions>
